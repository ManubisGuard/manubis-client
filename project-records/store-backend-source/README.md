# ManubisGuard Store Backend

Initial safe scaffold for the Store API and server-side panel adapter. It is not yet a complete shop and must not be exposed publicly as a production checkout service.

## Local setup

```bash
python3 -m venv .venv
. .venv/bin/activate
pip install -e '.[test]'
cp .env.example .env
# Set PANEL_API_KEY to a newly rotated, least-privilege key in this server-local file.
uvicorn app.main:app --host 127.0.0.1 --port 8091 --reload
```

- `/health/live` checks process liveness.
- `/health/ready` checks that the server-side panel key is configured and that PostgreSQL actually answers `SELECT 1`; it never returns secrets.
- `GET /api/v1/store/plans` returns active plans from PostgreSQL; panel template IDs remain private.
- SQLAlchemy models define plans and order-state fields. Alembic migrations `0001_initial_store_tables` and `0002_order_status_constraint` create the schema and enforce the documented order status set at the database layer. Migrations must be applied to a disposable/test database first; no production database has been migrated. Order/payment routes are not implemented yet.
- OpenAPI docs are enabled only outside `APP_ENV=production`.
- `GET /api/v1/admin/plans`, `POST /api/v1/admin/plans`, and `PATCH /api/v1/admin/plans/{id}` are protected by a separate `Authorization: Bearer ...` token configured as `ADMIN_API_TOKEN`; never reuse the panel API key.
- Admin plan edits support deactivation (`is_active=false`) instead of hard deletion. A lightweight browser dashboard is served at `/admin`; its privileged actions still require `ADMIN_API_TOKEN`. The dashboard response sends `Cache-Control: no-store, max-age=0`, `Pragma: no-cache`, a restrictive Content Security Policy, and common browser security headers; authenticated admin API responses also disable caching. These headers are defense-in-depth, not a substitute for HTTPS, rate limiting, audit logging, and trusted-proxy access controls.
- `app/panel/client.py` contains a server-side panel adapter. Live authenticated integration with the production panel has not been verified.

## Test deployment and CI

- `Dockerfile` builds a non-root API image; `compose.yaml` runs an isolated PostgreSQL + API stack with loopback-only port publishing by default, health checks, dropped Linux capabilities, read-only API filesystem, and no-new-privileges.
- Follow `DEPLOY_TEST.md` for the isolated test deployment. It requires independent secrets and never migrates the production database. The smoke script verifies liveness, admin page, public catalogue/settings, and unauthenticated admin denial.
- `.github/workflows/test.yml` runs PostgreSQL-backed migrations/schema checks, pytest, Python compile checks, and the dashboard JavaScript syntax check on GitHub Actions.

**Not production-ready:** customer authentication, user-owned subscriptions, order creation, a payment provider/webhook, idempotent fulfilment, provisioning after verified payment, audit logging, and admin rate limiting are not implemented. The admin API must remain network-restricted and must not be exposed publicly. The Android app still has local branding edits only; no verified APK build or Store UI integration exists.

Next: run the isolated Compose deployment, then create/confirm a dedicated Git repository for this backend before pushing. Verify the live panel API only with a newly rotated least-privilege key in staging. Never put panel credentials in the Android app.

## Store settings and plan administration

- The admin dashboard supports creating, editing, activating, and deactivating catalogue plans. Editing a plan changes the shop catalogue only; it does not itself provision or renew a customer subscription.
- `store_settings` is managed through authenticated `GET/PATCH /api/v1/admin/settings` and public `GET /api/v1/store/settings`. It contains only presentation/business settings: store name, description, default currency, optional HTTPS support URL, and a maintenance-mode flag. It never stores panel credentials.
- Migration `0003_store_settings` creates a singleton settings row with safe defaults. Migration `0004_panel_connection_settings` creates the singleton row for a managed panel URL and encrypted API key. Migrations must be tested on disposable PostgreSQL before any intended deployment.
- The admin dashboard now manages the panel connection through authenticated `GET/PATCH /api/v1/admin/panel/connection`. The API key is encrypted with Fernet before it enters PostgreSQL, never returned by the API, and never persisted in browser storage. Set a stable, secret `PANEL_SETTINGS_ENCRYPTION_KEY` generated by `python -c "from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())"` before saving managed credentials. Back up this key separately and do not rotate it without a planned decrypt/re-encrypt procedure; losing it makes stored credentials unreadable. A newly supplied, least-privilege panel API key is required for the first managed save. The legacy `PANEL_BASE_URL`/`PANEL_API_KEY` remain fallback settings when no managed database row exists.
- The URL validator requires an HTTPS origin without a path, disallows credentials/query/fragment, limits the port to 443, and rejects obvious local/reserved targets. It does not by itself eliminate DNS rebinding/SSRF risks; keep this admin API restricted to a trusted network/reverse proxy and use an approved panel hostname. Do not place panel API keys in public settings or the Android client.
